SQL Injection (SQLi) Anatomy & Fix

SQL Injection occurs when untrusted user input is directly concatenated into database query strings. Attackers manipulate the query structure to bypass login authentication, extract customer data, or drop entire database tables.

Context: FoodOrderingSystem Repository (Java JDBC vs Spring Data JPA `UserRepository`).

How Unsafe String Concatenation Breaks SQL Structure

When developers construct SQL queries by stitching strings together (e.g. "SELECT * FROM users WHERE email='" + email + "'"), the database SQL parser cannot distinguish between developer code and attacker data!

Malicious Input Example

Auth Bypass Payload

Attacker enters admin' OR '1'='1 into the email login input field.

// Java Backend String Concatenation: String sql = "SELECT * FROM users WHERE " + "email='" + userInput + "'"; // Resulting SQL Executed on DB Engine: SELECT * FROM users WHERE email='admin' OR '1'='1';

Result: '1'='1' is ALWAYS true! The WHERE clause matches the admin record and logs the attacker in without a password.

Parameterized Query Solution

PreparedStatement Binding

Using PreparedStatement placeholders (?) sends SQL query structure and parameter values separately.

// PreparedStatement Compiler Template: String sql = "SELECT * FROM users WHERE email=?"; PreparedStatement pstmt = conn.prepareStatement(sql); // Parameter bound as literal text: pstmt.setString(1, userInput);

Result: Database treats admin' OR '1'='1 strictly as a literal string. Looks for email literally equal to that text. Returns 0 rows safely!

Java JDBC & Spring Data JPA Code Patterns

How to eliminate SQL Injection across raw JDBC code, Spring JdbcTemplate, and Spring Data JPA Repositories:

❌ Vulnerable JDBC Code
public User findUser(String email, String password) { // DANGEROUS: Concatenation allows query altering! String sql = "SELECT * FROM users WHERE email='" + email + "' AND password='" + password + "'"; Statement stmt = connection.createStatement(); ResultSet rs = stmt.executeQuery(sql); return extractUser(rs); }
✅ Secure PreparedStatement (JDBC)
public User findUser(String email, String password) { // SAFE: Placeholders ? compile query template first String sql = "SELECT * FROM users WHERE email=? AND password=?"; PreparedStatement pstmt = connection.prepareStatement(sql); pstmt.setString(1, email); pstmt.setString(2, password); ResultSet rs = pstmt.executeQuery(); return extractUser(rs); }
✅ Secure Spring Data JPA Repository (FoodOrderingSystem)

Spring Data JPA automatically parameterizes derived finder methods and JPQL @Query parameters:

public interface UserRepository extends JpaRepository<User, Long> { // SAFE: Automatically generated parameterized SQL query Optional<User> findByEmailAndPassword(String email, String password); // SAFE: JPQL with named parameter binding @Query("SELECT u FROM User u WHERE u.email = :email") Optional<User> findCustomByEmail(@Param("email") String email); }

SQL Injection Prevention Best Practices

1. Parameterized Queries

Always use PreparedStatement or ORM frameworks like Hibernate / Spring Data JPA. Never build SQL queries using raw string concatenation.

2. Principle of Least Privilege

Configure backend database connection credentials with restricted permissions. The app DB user should NOT have DROP TABLE or administrative DBA rights.

3. Input Validation & Allowlisting

Validate input format, pattern, length, and character set using Bean Validation annotations (e.g. @Email, @Pattern). Reject invalid characters before querying.

4. Stored Procedures

Where legacy relational DB operations are required, wrap logic in Stored Procedures which enforce parameter type safety natively.
