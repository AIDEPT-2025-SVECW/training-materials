The 5 NIST Essential Characteristics of Cloud Computing

According to the National Institute of Standards and Technology (NIST SP 800-145)—which is heavily referenced in Capgemini exams—a system MUST possess these five characteristics to be classified as a true Cloud service:

Characteristic #1
1. On-Demand Self-Service
Users can provision compute, storage, or database resources automatically via a web portal or API without human intervention from cloud support engineers.
Example: Launching an AWS EC2 instance in 30 seconds via AWS Console.
Characteristic #2
2. Broad Network Access
Cloud capabilities are accessible over standard network mechanisms (Internet/WAN) using heterogeneous client platforms (laptops, mobile phones, IoT devices, web browsers).
Example: Accessing REST APIs from mobile iOS apps and desktop web apps.
Characteristic #3
3. Resource Pooling (Multi-Tenancy)
Provider compute resources are pooled to serve multiple customers (tenants) using a multi-tenant model. Physical resources are dynamically assigned and reassigned based on demand.
Example: Multiple companies sharing the same physical server hardware securely via hypervisors.
Characteristic #4
4. Rapid Elasticity
Capabilities can be elastically provisioned and released—automatically or manually—to scale rapidly outward and inward with demand. To the user, available resources appear infinite.
Example: Auto Scaling Groups expanding server count from 2 to 20 during Black Friday.
Characteristic #5
5. Measured Service
Resource usage (CPU hours, bandwidth, storage gigabytes) is automatically monitored, controlled, and reported. This enables transparent pay-per-use (metered) billing.
Example: Receiving a detailed AWS monthly bill itemized by gigabyte-hours used.

Elasticity vs. Scalability

Candidates frequently confuse Scalability with Elasticity. Here is the definitive distinction for technical exams:

Scalability (Long-Term Growth)

Ability to Handle Increased Load

Scalability is the infrastructure's capacity to accommodate growth over weeks or months by adding resources.

  • Vertical Scaling (Scale-Up): Adding more CPU/RAM to an existing server (e.g. upgrading from 4GB to 32GB RAM). Has a hardware limit!
  • Horizontal Scaling (Scale-Out): Adding more server nodes to a load balancer (e.g. going from 2 servers to 10 servers). Infinite potential!
Elasticity (Real-Time Adaptability)

Dynamic Scale-In & Scale-Out

Elasticity is the system's ability to automatically expand AND contract resources in real-time to match fluctuating hourly workload demand.

  • Scales UP automatically when CPU exceeds 80%.
  • Scales DOWN automatically when traffic drops at night to save costs.
  • Key Metric: Time-to-provision & Cost Efficiency.

🧠 Capgemini Exam Summary Rule:

"All elastic systems are scalable, but NOT all scalable systems are elastic!"
A database that can take 6 months to add 10 new hard drives is Scalable, but NOT Elastic because it cannot scale down automatically when traffic drops.

High Availability (HA), Fault Tolerance & Service Level Agreement (SLA) Math

High Availability (HA) ensures an application remains accessible without interruption even during component failures. A Service Level Agreement (SLA) is a formal contract between a cloud provider (e.g., AWS, Azure, GCP) and a customer defining guaranteed uptime metrics and financial service credits awarded if downtime occurs.

Availability vs Reliability

Core Definitions

Availability: Percentage of total time a system is functional and accessible (Uptime vs Total Time).
Reliability: Probability that a system will perform without failure for a specified duration (measured by Mean Time Between Failures - MTBF).

Disaster Recovery (DR)

RTO & RPO Metrics

RTO (Recovery Time Objective): Maximum acceptable duration of system downtime after an outage.
RPO (Recovery Point Objective): Maximum acceptable amount of data loss measured in time (e.g. last 15 min backup).

Service Level Agreement (SLA) Uptime & Allowed Downtime Table ("The Nines")

Capgemini & IT technical exams frequently ask candidates to calculate max allowed downtime for specific Service Level Agreements (SLAs):

SLA Percentage Uptime Rating Allowed Downtime / Year Allowed Downtime / Month
99% ("Two Nines") Standard Web App 3.65 days 7.31 hours
99.9% ("Three Nines") Production Cloud App 8.77 hours 43.8 minutes
99.99% ("Four Nines") Enterprise Mission-Critical 52.6 minutes 4.38 minutes
99.999% ("Five Nines") Carrier-Grade Telecom/Banking 5.26 minutes 26.3 seconds
Reference Note: Standard Matrix vs. Cloud Provider Examples

📌 Standard Mathematical Matrix: The downtime durations in the table above represent the universal mathematical standard calculated using the formula: Allowed Downtime = (100% - SLA%) × Total Time (where 1 Year = 525,600 minutes and 1 Month = 43,200 minutes).

🌐 Real-World Cloud Provider Benchmark References (AWS / Azure / GCP):

  • 99.99% ("Four Nines"): AWS EC2 Multi-AZ / Azure VM Availability Zones SLA (Max ~4.38 min/month downtime guarantee).
  • 99.9% ("Three Nines"): AWS EC2 Single Instance / Google Compute Engine Single-Zone SLA.
  • 99.99% Availability & 99.999999999% ("11 Nines") Durability: Amazon S3 Standard & Azure Blob Storage.
  • 100% Availability SLA: AWS Route 53 DNS & Azure DNS global resolution guarantee.

Cloud Deployment Models (Public, Private, Hybrid, Multi-Cloud)

1. Public Cloud

Multi-Tenant Shared Vendor Infra

Infrastructure owned and managed by third-party cloud providers (AWS, GCP, Azure) accessible over the public Internet.

2. Private Cloud

Single-Tenant Dedicated Infra

Infrastructure operated solely for a single organization, hosted on-premises or by a third party with dedicated hardware.

3. Hybrid Cloud

Combined On-Prem + Public Cloud

Integrates private data centers with public cloud infrastructure via VPN/Direct Connect for security & compliance.

4. Multi-Cloud

Multiple Vendor Providers

Using services from two or more public cloud vendors (e.g. AWS for compute + GCP for AI BigQuery) to prevent vendor lock-in.
