⚖️ Step 1 — The Architecture Shift

Single Server vs. Load Balancer + Multiple Replicas

Why modern web applications never rely on a single backend server instance.

Old Way — Single Instance

Single Point of Failure (SPOF)

All user traffic flows to 1 single backend server instance.

  • If traffic spikes, CPU hits 100% and crashes the app for ALL users.
  • If server hardware fails or reboots, 100% downtime occurs.
  • Deploying new code updates requires stopping the server (downtime).
Modern Way — LB + Pool of Replicas

High Availability & Horizontal Scale

A Load Balancer distributes traffic evenly across N identical server replicas.

  • Traffic is evenly split so no single replica gets overloaded.
  • If Server A crashes, Load Balancer immediately redirects traffic to Server B & C.
  • Enables Zero-Downtime Deployments (Rolling updates one replica at a time).
🔄 Step 2 — Load Balancing Algorithms

How Does the Load Balancer Decide Where to Send Traffic?

Click through the 4 core routing algorithms commonly asked in tech interview questions!

1. Round Robin (Default & Simplest)

Requests are distributed sequentially in a strict circle: Request 1 ➔ Server A, Request 2 ➔ Server B, Request 3 ➔ Server C, Request 4 ➔ Server A.

💡 Best used when all backend server replicas have identical CPU/RAM capacities.

🌐 Step 3 — OSI Layer Types

Layer 4 (L4) vs. Layer 7 (L7) Load Balancers

Non-Tech Analogy for Freshers (No Networking Knowledge Required!)

✉️ Layer 4 (L4) = Sealed Envelope Mail Clerk

The clerk only looks at the address written on the outside of the envelope (IP Address & Port Number). They NEVER open the letter. They quickly pass the envelope to Counter 1 or Counter 2. Lightning fast, but blind to what's inside the message!

🧠 Layer 7 (L7) = Smart Department Store Receptionist

The receptionist opens the request and reads what the customer actually wants. Asking for /shoes? Sent to Floor 2. Asking for /food? Sent to Floor 1. Holding a VIP Coupon (Cookie)? Sent to the VIP Counter! Smart, context-aware routing!

Layer 4 Load Balancer (Network Level)

Operates at the Transport Layer (TCP/UDP). Routes packets purely based on IP addresses and Port numbers without inspecting HTTP contents.

  • ⚡ Ultra-fast & high throughput (low CPU overhead).
  • Cannot route based on URL path or HTTP cookies.
  • Example: AWS Network Load Balancer (NLB), HAProxy L4 mode.

Layer 7 Load Balancer (Application Level)

Operates at the Application Layer (HTTP/HTTPS). Inspects HTTP headers, cookies, and URL paths to route traffic intelligently.

  • 🧠 Smart URL routing: /api/orders ➔ Order Pool, /images ➔ Media Pool.
  • Supports SSL/TLS termination & HTTP Cookie stickiness.
  • Example: AWS Application Load Balancer (ALB), NGINX.

💓 Step 4 — Active Monitoring

Health Checks & Automatic Failover

How the Load Balancer knows which server replicas are healthy and which ones are dead!

The Load Balancer continuously pings a heartbeat endpoint (e.g. GET /healthz) on every replica every 5 seconds. If a replica responds with HTTP 200 OK, it stays in the target group. If it fails 3 consecutive pings, it gets automatically evicted!

Server Replica 1
🟢 GET /healthz ➔ 200 OK
Server Replica 2
🟢 GET /healthz ➔ 200 OK
Server Replica 3
🔴 GET /healthz ➔ 500 / TIMEOUT!
⚠️ Auto-Eviction Action: Replica 3 failed 3 consecutive health checks! Load Balancer immediately stops sending user requests to Replica 3 and redirects 100% traffic to Replica 1 & 2.
