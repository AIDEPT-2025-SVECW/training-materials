Understanding Scaling Strategies

As user traffic grows, application servers and databases experience CPU spikes, memory exhaustion, and response latency. Software engineers use two fundamental approaches to handle increased load:

Vertical Scaling (Scale-Up)

Upgrade Single Machine Hardware

Increasing the physical capacity of an existing single server by adding more vCPUs, RAM, or faster NVMe SSD storage (e.g. upgrading an AWS EC2 instance from t3.medium with 4GB RAM to m5.4xlarge with 64GB RAM).

  • ✅ Zero Code Changes: Monolithic apps run unchanged without needing distributed sessions.
  • ✅ Simplicity: No load balancers or network inter-process communication required.
  • ❌ Hardware Ceiling: Physical limit on max RAM/CPU a single motherboard can hold.
  • ❌ Single Point of Failure (SPOF): If the server hardware crashes, the entire system goes down!
  • ❌ Downtime Required: Resizing a server requires restarting the VM instance.
Horizontal Scaling (Scale-Out)

Add Parallel Server Nodes

Adding more commodity server instances into a resource pool behind an Elastic Load Balancer (ELB). Instead of 1 massive server, traffic is distributed across 10 smaller worker nodes.

  • ✅ Infinite Scalability: Add as many server nodes as needed to handle millions of requests.
  • ✅ High Availability & Fault Tolerance: If 1 node fails, the load balancer routes traffic to remaining healthy nodes.
  • ✅ Zero Downtime Upgrades: Rolling updates allow patching servers one by one without taking the app offline.
  • ❌ Architecture Complexity: Requires stateless session management (JWT / Redis session store).
  • ❌ Network Overhead: Requires Load Balancer setup and distributed data synchronization.

Database Scaling: Relational (RDBMS) vs. NoSQL

Scaling databases is significantly harder than scaling web servers because databases maintain state on disk!

Scaling RDBMS (PostgreSQL / MySQL)

Vertical Primary + Read Replicas

Relational databases rely on ACID transactions, making multi-master horizontal writes difficult.

  • Write Path: Scaled vertically on 1 Primary DB master node.
  • Read Path: Scaled horizontally using asynchronous Read Replicas.
  • Advanced Sharding: Partitioning table rows across multiple DB instances by Shard Key.
Scaling NoSQL (MongoDB / DynamoDB)

Native Horizontal Sharding

NoSQL databases relax strict ACID constraints (BASE model) to achieve seamless horizontal scaling across clusters.

  • Automatic Sharding: Data distributed across nodes using Partition Keys.
  • High Throughput: Reads and writes scale horizontally automatically.
  • Use Case: Real-time food order tracking, user session stores, chat logs.
