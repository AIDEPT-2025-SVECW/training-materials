Access Control Across Java Packages

Master how packages define strict encapsulation perimeters. Understand package-private, protected inheritance boundaries, and enterprise security.

🔒 Package-Private Default 🛡️ Protected Inheritance 🏛️ Banking Security Model
❓

1. WHY: Why Does Package Scope Exist?

Languages like C++ only have public, protected, and private. Java deliberately introduced a 4th level: Package-Private (Default):

The Public Exposure Dilemma

Suppose you are building the State Bank of India (SBI) core banking module. Inside package in.sbi.core, you have Account.java and an internal helper InterestCalculator.java. If you make the helper public, third-party apps can call it and alter interest calculations!

The Package Boundary Solution

By declaring InterestCalculator with default (package-private) visibility, it is accessible to all classes within in.sbi.core, but 100% invisible and inaccessible to any class outside the package.

💡

2. WHAT: The Master Visibility Matrix

Access Modifier Same Class Same Package Subclass Same Package Non-Subclass Different Package Subclass Different Package Non-Subclass
public YES YES YES YES YES
protected YES YES YES YES (via inheritance) NO
default (no modifier) YES YES YES NO NO
private YES NO NO NO NO
🔑
The Protected Gotcha: When accessing a protected member from another package in a subclass, you can only access it through super.member or on an instance of the subclass itself—never on a reference to the parent class!
🛠️

3. HOW: SBI Core Banking Security Architecture

Let's see how State Bank of India uses package boundaries to safeguard ledger entries:

in/sbi/core/BankAccount.java (Package 1: Core Domain)
package in.sbi.core;

public class BankAccount {
    public String accountNumber;          // 1. Public: Available everywhere
    protected double balance;             // 2. Protected: Available to SBI subclasses in any package
    int branchRoutingCode;                // 3. Default: Only available inside in.sbi.core
    private String transactionPin;        // 4. Private: Only inside BankAccount itself

    public BankAccount(String accNo, double bal, int routingCode, String pin) {
        this.accountNumber = accNo;
        this.balance = bal;
        this.branchRoutingCode = routingCode;
        this.transactionPin = pin;
    }
}
in/sbi/premium/SbiWealthAccount.java (Package 2: Subclass)
package in.sbi.premium;

import in.sbi.core.BankAccount;

public class SbiWealthAccount extends BankAccount {

    public SbiWealthAccount(String accNo, double initialDeposit) {
        super(accNo, initialDeposit, 560001, "8822");
    }

    public void applyRelationshipManagerBonus() {
        // ✅ ALLOWED: 'balance' is protected, accessible through inheritance!
        this.balance += 5000.00; 

        // ❌ COMPILE ERROR: 'branchRoutingCode' is default, NOT accessible outside in.sbi.core!
        // System.out.println(this.branchRoutingCode);

        // ❌ COMPILE ERROR: 'transactionPin' is private!
        // System.out.println(this.transactionPin);

        System.out.println("SBI Wealth Bonus applied! Updated Balance: ₹ " + this.balance);
    }
}

📌 Key Takeaways

  • Why: Modifiers establish defense-in-depth security and architectural isolation across packages.
  • What: public (global), protected (package + external subclasses), default (package-only), private (class-only).
  • How: Keep helper classes and methods package-private so internal implementation details do not leak into consumer APIs.
