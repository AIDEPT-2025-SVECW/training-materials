Types of Exceptions: Checked vs Unchecked

Master the fundamental dichotomy in Java exception handling: compile-time enforced Checked exceptions versus runtime Unchecked exceptions, plus custom business exceptions.

📜 Checked (Compile-Time) ⚡ Unchecked (Runtime) 🎯 Custom Exceptions
❓

1. WHY: Why Does Java Have Two Distinct Categories of Exceptions?

Java is known for its strong compile-time type safety. The designers recognized that exceptions fall into two fundamentally different scenarios:

🛂 1. Outside the Program's Control (Checked)

When your code reaches outside the JVM—reading a file from a pen drive, connecting to an SBI database server across the internet, or making a third-party API call—the external world might fail even if your Java code is 100% bug-free. The Java compiler forces you up-front to write a fallback plan.

🐛 2. Programmer Mistakes & Logic Bugs (Unchecked)

When a programmer tries to access index 10 of a 5-element array, or divides a number by zero, or accesses a null object, this is simply a logic mistake. Forcing developers to surround every single array lookup or math calculation with try-catch would make code completely unreadable.

💡

2. WHAT: Detailed Comparison (Checked vs Unchecked)

Feature 📜 Checked Exceptions ⚡ Unchecked Exceptions
Inheritance Parent Directly extends java.lang.Exception (excluding RuntimeException). Extends java.lang.RuntimeException.
Detection Time Checked at Compile-Time by javac. Occurs strictly at Runtime during program execution.
Compiler Requirement Mandatory. You MUST handle via try-catch OR declare with throws. Code will not compile otherwise! Optional. The compiler never forces you to catch or declare them.
Cause External environmental conditions (network, filesystem, database, hardware). Internal programming flaws, bad algorithms, or missed data validation checks.
How to Prevent Cannot be 100% prevented by code alone; must be handled with fallback code. Can and should be prevented by writing proper validation logic (e.g. if (obj != null)).

Memorable Real-World Analogy:
• Checked Exception: Carrying a valid Passport before boarding an international flight at Mumbai Airport. The security officers (the compiler) check you before you are even allowed inside the terminal.
• Unchecked Exception: Slipping on a wet airport tile while walking to the gate. No security guard can check for this at the entrance; it happens suddenly at runtime!

3. HOW: IRCTC Tatkal Passenger Verification (Checked + Unchecked + Custom)

In enterprise software, developers also create Custom (User-Defined) Exceptions to represent domain-specific business rules. Here is a clean IRCTC Tatkal booking example demonstrating:

  • Custom Checked Exception (extends Exception): SeniorCitizenAgeException
  • Built-in Unchecked Exception: NumberFormatException (invalid Aadhaar digits)
IrctcBookingDemo.java (Indian Enterprise Context)
// 1. CUSTOM CHECKED EXCEPTION: Extends Exception
// The compiler forces calling methods to handle or declare this!
class SeniorCitizenQuotaException extends Exception {
    public SeniorCitizenQuotaException(String message) {
        super(message);
    }
}

public class IrctcBookingDemo {

    // Method declaring checked exception using 'throws' keyword
    public static void bookSeniorCitizenBerth(String passengerName, int age) 
            throws SeniorCitizenQuotaException {

        System.out.println("Validating concession quota for: " + passengerName);

        if (age < 60) {
            // Explicitly throwing our custom checked exception using 'throw':
            throw new SeniorCitizenQuotaException(
                "Denied: Age is " + age + ". Senior Citizen quota requires age >= 60!"
            );
        }
        System.out.println("✅ Lower Berth Allocated to: " + passengerName);
    }

    public static void main(String[] args) {
        System.out.println("--- 🇮🇳 IRCTC Indian Railway Reservation Portal ---");

        // Scenario A: Handling Unchecked Exception (NumberFormatException)
        try {
            String enteredAge = "forty-five"; // Invalid user input!
            int parsedAge = Integer.parseInt(enteredAge); // Throws NumberFormatException
            System.out.println("Parsed Age: " + parsedAge);
        } catch (NumberFormatException ex) {
            System.out.println("⚡ [Unchecked Exception Handled]: Age must contain only digits 0-9.");
        }

        // Scenario B: Handling Custom Checked Exception
        try {
            bookSeniorCitizenBerth("Ramesh Gupta", 52);
        } catch (SeniorCitizenQuotaException ex) {
            System.out.println("📜 [Checked Exception Handled]: " + ex.getMessage());
        }

        System.out.println("--- Booking session completed safely ---");
    }
}

📌 Key Takeaways for Freshers

  • Checked Exceptions: Extend Exception. Checked by javac at compile-time. Mandatory to catch or declare with throws.
  • Unchecked Exceptions: Extend RuntimeException. Arise from coding bugs. Optional to catch, but should be prevented using defensive checks.
  • Custom Exceptions: Extend Exception if you want the compiler to enforce handling of your business rule; extend RuntimeException if you don't.
