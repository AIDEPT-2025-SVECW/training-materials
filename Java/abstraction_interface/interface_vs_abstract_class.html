Interface vs Abstract Class

The definitive guide to OOP architecture: exhaustive feature comparison, IS-A vs CAN-DO design rules, and the industry-standard Skeletal Implementation Pattern.

⚖️ Architectural Decision 🧬 IS-A vs CAN-DO 🏛️ Skeletal Implementation
📊

1. The Comprehensive Comparison Matrix

Even after Java 8 added default and static methods to interfaces, significant differences in state, lifecycle, and inheritance remain:

Feature / Parameter Abstract Class Interface
Inheritance Model Single inheritance: A class can extend only one abstract class (extends). Multiple inheritance: A class can implement multiple interfaces (implements A, B, C).
State / Instance Fields Can have mutable instance variables, static variables, and constants. No instance state! Variables are strictly public static final constants.
Constructors Yes! Can define constructors (invoked by subclasses via super()). No! Cannot declare constructors; cannot hold non-static state.
Method Access Modifiers Can have public, protected, default, and private methods. Methods are public by default. Java 9 added private methods for helper code.
Design Relationship "IS-A" relationship. Represents high identity sharing among closely related classes. "CAN-DO" / Capability. Represents contracts shared across completely unrelated classes.
Speed / Performance Slightly faster method dispatch via direct class virtual method table (vtable). Minor lookup overhead via interface method table (itable) due to multiple inheritance polymorphism.
API Evolution (Adding methods) Can easily add concrete methods without breaking existing subclasses. Pre-Java 8 would break all implementors; Java 8+ requires default methods to evolve safely.
🎯

2. Architecture Decision: When to Choose Which?

Choose an Abstract Class When:

  • You need to share common mutable state (fields like id, timestamp, connectionPool).
  • You have closely related classes that represent a clear family hierarchy (e.g., Cat, Dog, Horse extending Animal).
  • You need protected or package-private helper methods that should NOT be visible to outside consumers.
  • You need to execute constructor logic when child objects are instantiated.

Choose an Interface When:

  • You need to define a common capability among completely unrelated classes (e.g., Bird and Airplane implementing Flyable).
  • You want to take advantage of multiple inheritance of type.
  • You want to decouple the public contract from the implementation (e.g., in Dependency Injection / Spring Framework).
  • You are writing a standard library API where client classes may already have their own inheritance hierarchy.

4. The Industry Best Practice: Skeletal Implementation Pattern

Why choose between an Interface and an Abstract Class when you can use both? In Joshua Bloch's renowned book Effective Java, this is called the Skeletal Implementation (Adapter) Pattern.

How Java's JDK Collections Framework Uses This:

1. interface List<E>: Defines the pure public contract and allows multiple inheritance.
2. abstract class AbstractList<E> implements List<E>: Provides default algorithmic plumbing for methods like equals(), hashCode(), and indexOf().
3. class ArrayList<E> extends AbstractList<E>: Focuses solely on array resizing and index lookups!

CharacterAction.java (Pure Contract)
// 1. The Interface: Defines the full contract & allows multiple inheritance
interface CharacterAction {
    void attack();
    void defend();
    void levelUp();
}
AbstractCharacter.java (Skeletal Implementation)
// 2. Skeletal Abstract Class: Implements shared state & boilerplate logic
abstract class AbstractCharacter implements CharacterAction {
    protected String name;
    protected int level = 1;

    public AbstractCharacter(String name) {
        this.name = name;
    }

    @Override
    public void levelUp() {
        level++;
        System.out.println(name + " leveled up to Level " + level + "!");
    }
}
Warrior.java (Concrete Subclass)
// 3. Concrete Class: Inherits boilerplate and implements only unique mechanics!
class Warrior extends AbstractCharacter {
    public Warrior(String name) {
        super(name);
    }

    @Override
    public void attack() {
        System.out.println(name + " swings huge battleaxe!");
    }

    @Override
    public void defend() {
        System.out.println(name + " raises heavy iron shield!");
    }
}
SkeletalDemo.java (Driver & Output)
public class SkeletalDemo {
    public static void main(String[] args) {
        // Client interacts via the pure Interface contract
        CharacterAction hero = new Warrior("Thorin Oakenshield");

        hero.attack();   // Thorin Oakenshield swings huge battleaxe!
        hero.defend();   // Thorin Oakenshield raises heavy iron shield!
        hero.levelUp();  // Thorin Oakenshield leveled up to Level 2! (From Skeletal Class)
    }
}

CompleteSkeletalPattern.java
// 1. Interface (Contract)
interface CharacterAction {
    void attack();
    void defend();
    void levelUp();
}

// 2. Skeletal Implementation (Abstract Adapter)
abstract class AbstractCharacter implements CharacterAction {
    protected String name;
    protected int level = 1;

    public AbstractCharacter(String name) { this.name = name; }

    @Override
    public void levelUp() {
        level++;
        System.out.println(name + " leveled up to Level " + level + "!");
    }
}

// 3. Concrete Subclass
class Warrior extends AbstractCharacter {
    public Warrior(String name) { super(name); }

    @Override
    public void attack() { System.out.println(name + " swings huge battleaxe!"); }

    @Override
    public void defend() { System.out.println(name + " raises heavy iron shield!"); }
}

// 4. Client Driver
public class SkeletalDemo {
    public static void main(String[] args) {
        CharacterAction hero = new Warrior("Thorin Oakenshield");
        hero.attack();
        hero.defend();
        hero.levelUp();
    }
}
