What is Encapsulation & Why Do We Need It?

The Capsule Concept

Encapsulation is the mechanism of bundling data fields (variables) and the methods that operate on them into a single class unit, while restricting direct access to internal state from the outside world (**Data Hiding**).

1. Data Integrity
Security

Prevents external code from corrupting object state (e.g. setting a negative bank balance or invalid age).

2. Controlled Access
Validation

Allows making fields Read-Only, Write-Only, or applying strict validation before modifying state.

THE ENCAPSULATED CLASS VAULT
🔒 Outer Public Interface
deposit() withdraw() getBalance()
🛡️ private double balance;
External code cannot touch balance directly. It MUST go through public methods!
2
The Danger: Unencapsulated Code & State Corruption

When instance fields are declared public, external code can tamper with object state directly. This bypasses all business logic, validation, and security!

// Dangerous Unencapsulated Class
public class UnsafeBankAccount {
  public String accountNumber;
  public double balance; // DANGEROUS! Public field!
}

// External Client Code (Tampering!)
UnsafeBankAccount acc = new UnsafeBankAccount();
acc.balance = -999999.0; // 💥 CORRUPTED NEGATIVE BALANCE!
acc.balance = 0.0; // 💥 WIPED OUT WITHOUT LOGS!

The Solution: Encapsulated Design (Private Fields + Validated Methods)

To solve state corruption, follow the 3-Step Encapsulation Recipe:

Step 1: Private Fields
private

Declare all instance fields as private so external code cannot read or modify them directly.

Step 2: Public Getters
get...()

Provide public getter methods to allow controlled read access to field values.

Step 3: Validated Setters
set...()

Provide public methods with validation checks (e.g. if (amount > 0)) to guard state mutations.

// Safe Encapsulated Class
public class EncapsulatedBankAccount {
  private double balance = 1000.0; // Private!

  // Public Getter (Controlled Read)
  public double getBalance() {
    return this.balance;
  }

  // Public Mutator with Validation Guard
  public void deposit(double amount) {
    if (amount > 0) {
      this.balance += amount; // Validated mutation
    } else {
      System.out.println("Invalid deposit amount!");
    }
  }
}

Side-by-Side Architectural Comparison
Architecture Aspect ❌ Unencapsulated Design ✅ Encapsulated Design
Field Modifier public double balance; private double balance;
External Field Access Direct access from anywhere (acc.balance) Restricted. Accessed via getters (acc.getBalance())
Data Validation None. External code can set any invalid value. Full control inside setter/deposit methods.
Refactoring Safety Brittle. Renaming fields breaks all client code. Flexible. Field names can change without affecting client code.
Security & Audit No audit logs or access tracking possible. Logs and security checks can be added inside mutators.
