Synchronized Methods & Synchronized Blocks in Java

Master Java's built-in locking mechanisms. Compare coarse-grained synchronized methods with fine-grained synchronized blocks, understand lock scopes (this vs. private lock vs. class-level), and discover how lock reentrancy prevents self-deadlock.

1. The Object Monitor Lock & Synchronization Scopes

Foundations

Every single Java object instance created in memory possesses an invisible built-in lock called an Intrinsic Lock or Monitor Lock. When you use the synchronized keyword, Java requires the thread to acquire this monitor lock before executing code.

1. Instance Method

public synchronized void m()

Locks on this (the calling object instance).

2. Synchronized Block

synchronized(lockObject) { }

Locks on the specific object passed inside parentheses.

3. Static Method

public static synchronized void m()

Locks on the ClassName.class object (Class-level lock).

📦

2. Synchronized Methods (Coarse-Grained Locking)

Method-Level

Simply adding the synchronized keyword to an instance method's declaration tells the JVM to guard the entire method body using the calling instance (this) as the lock:

SynchronizedMethodExample.java
class Printer {
    // The entire method is synchronized on 'this'
    public synchronized void printDocument(String docName) {
        System.out.println("Printing started: " + docName);
        for (int i = 1; i <= 3; i++) {
            System.out.println("  Page " + i + " of " + docName);
        }
        System.out.println("Printing finished: " + docName);
    }
}

✓ Advantage:

Extremely simple and readable. Ideal when the entire method is purely dedicated to updating shared mutable fields.

✗ Major Drawback (Coarse-Grained):

If the method performs expensive calculations, database lookups, or file I/O, other threads are forced to sit idle in the BLOCKED state waiting, crushing application throughput!

🎯

3. Synchronized Blocks (Fine-Grained Locking)

Best Practice

A Synchronized Block allows you to lock only the exact critical section where shared fields are modified, allowing non-critical operations (like input parsing, calculations, or logging) to run concurrently in parallel:

SynchronizedBlockExample.java
class OrderProcessor {
    private int totalOrders = 0;
    private final Object lock = new Object(); // Private lock object

    public void processOrder(String orderId) {
        // 1. Heavy computation runs CONCURRENTLY on multiple threads!
        System.out.println("Validating order data for: " + orderId);

        // 2. Only the tiny critical section acquires the lock:
        synchronized (lock) {
            totalOrders++; // Protected update!
        }

        // 3. Post-processing runs CONCURRENTLY again!
        System.out.println("Confirmation sent for: " + orderId);
    }
}

Throughput Comparison: Method vs. Block:

Synchronized Method:
Thread 1 Holds Lock for Entire Method (500 ms) — Thread 2 BLOCKED
Synchronized Block:
Parallel Prep (200ms) Lock (20ms) Parallel Done (200ms)

💡 With synchronized blocks, threads execute 90% of their logic simultaneously in parallel on separate silicon cores!

🛡️

4. The Private Final Lock Pattern (Industry Standard)

Security Pattern

Students frequently write synchronized(this). While functional, it has a serious architectural risk:

⚠️
The Danger of synchronized(this):
this is a publicly exposed reference. Any external code that holds a reference to your object can write synchronized(myObject) { ... } and accidentally freeze or deadlock your entire service!

✓ The Solution: Private Final Lock

private final Object lock = new Object();

public void update() {
    synchronized (lock) {
        // Fully encapsulated!
    }
}

Because lock is private, external classes cannot see or synchronize on it. Because it is final, the lock reference can never be reassigned mid-execution.

🚫 Warning: Never Lock on Strings or Boxed Primitives!

Never write synchronized("MY_LOCK") or synchronized(Integer.valueOf(1))!

• String Pool: Identical string literals share the exact same object across the entire JVM.
• Integer Cache: Integers between -128 and 127 are cached.
Unrelated third-party libraries synchronizing on the same literal will cause cross-application deadlocks!

⚖️

Comparison

6. Lock Reentrancy (Reentrant Synchronization)

Self-Deadlock Prevention

What happens if a thread that already holds a lock calls another method that requires the exact same lock?

💡
Java Locks are Reentrant:
"A thread cannot deadlock itself on a lock it already owns."
When a thread attempts to acquire a monitor lock it already holds, the JVM simply increments an internal acquisition counter and allows the thread to proceed immediately.
Thread enters outer() ──► Acquires Lock [Count = 1] │ ▼ Thread calls inner() ──► Re-enters SAME Lock! [Count = 2] (Allowed! No deadlock) │ ▼ Thread exits inner() ──► Decrements Lock [Count = 1] │ ▼ Thread exits outer() ──► Decrements Lock [Count = 0] ──► Lock fully released for other threads!
💻

7. Complete Verified Java Demo: SynchronizedMethodsAndBlocksDemo.java

Verified Java 17 Demo

The following self-contained program demonstrates synchronized methods, synchronized blocks with private locks, and lock reentrancy with simple, clear console prints:

SynchronizedMethodsAndBlocksDemo.java
/**
 * Synchronized Methods & Synchronized Blocks Demonstration
 * 
 * Demonstrates:
 * 1. Synchronized Instance Method (locks on 'this')
 * 2. Synchronized Block with Private Lock (fine-grained locking)
 * 3. Static Synchronized Method (locks on ClassName.class)
 * 4. Reentrant Nature of Java Intrinsic Locks
 */
public class SynchronizedMethodsAndBlocksDemo {

    // 1. Synchronized Instance Method
    static class InstanceSyncDemo {
        public synchronized void printNumbers(String threadName) {
            System.out.println("  [" + threadName + "] Entered synchronized method (Lock: this)");
            for (int i = 1; i <= 3; i++) {
                System.out.println("  [" + threadName + "] Method count: " + i);
                try { Thread.sleep(50); } catch (InterruptedException ignored) {}
            }
            System.out.println("  [" + threadName + "] Exiting synchronized method");
        }
    }

    // 2. Synchronized Block with Private Lock (Fine-Grained)
    static class BlockSyncDemo {
        private final Object lock = new Object(); // Private lock object

        public void executeTask(String threadName) {
            // Unsynchronized section runs concurrently!
            System.out.println("  [" + threadName + "] Concurrent preparation (outside lock)");

            // Synchronized block: only this critical section is locked
            synchronized (lock) {
                System.out.println("  [" + threadName + "] >> ENTERED synchronized block (Lock: private lock)");
                for (int i = 1; i <= 2; i++) {
                    System.out.println("  [" + threadName + "] >> Critical work: " + i);
                    try { Thread.sleep(50); } catch (InterruptedException ignored) {}
                }
                System.out.println("  [" + threadName + "] >> EXITED synchronized block");
            }
        }
    }

    // 3. Reentrant Lock Demonstration
    static class ReentrantDemo {
        public synchronized void outerMethod() {
            System.out.println("  [OuterMethod] Acquired lock. Now calling innerMethod()...");
            innerMethod(); // Re-enters synchronized method on the SAME lock!
            System.out.println("  [OuterMethod] Successfully completed innerMethod()");
        }

        public synchronized void innerMethod() {
            System.out.println("  [InnerMethod] Successfully re-entered with same lock! No deadlock occurred.");
        }
    }

    public static void main(String[] args) throws InterruptedException {
        System.out.println("==========================================================");
        System.out.println("   SYNCHRONIZED METHODS & BLOCKS: CONCURRENCY DEMO        ");
        System.out.println("==========================================================");

        // --- 1. Synchronized Method Test ---
        System.out.println("\n--- 1. Testing Synchronized Instance Method ---");
        InstanceSyncDemo methodDemo = new InstanceSyncDemo();
        Thread t1 = new Thread(() -> methodDemo.printNumbers("Thread-1"));
        Thread t2 = new Thread(() -> methodDemo.printNumbers("Thread-2"));
        t1.start(); t2.start();
        t1.join(); t2.join();

        // --- 2. Synchronized Block Test ---
        System.out.println("\n--- 2. Testing Synchronized Block (Fine-Grained) ---");
        BlockSyncDemo blockDemo = new BlockSyncDemo();
        Thread t3 = new Thread(() -> blockDemo.executeTask("Thread-A"));
        Thread t4 = new Thread(() -> blockDemo.executeTask("Thread-B"));
        t3.start(); t4.start();
        t3.join(); t4.join();

        // --- 3. Reentrant Lock Test ---
        System.out.println("\n--- 3. Testing Lock Reentrancy ---");
        ReentrantDemo reentrantDemo = new ReentrantDemo();
        reentrantDemo.outerMethod();

        System.out.println("\n==========================================================");
        System.out.println("All synchronization mechanisms demonstrated successfully!");
        System.out.println("==========================================================");
    }
}

8. Frequently Asked Questions & Interview Concepts

Interview Preparation

Click any question to reveal the comprehensive interview-grade answer:

Q1. What is the difference between a synchronized method and a synchronized block? ▼
Answer:
• Scope: A synchronized method locks the entire method from start to finish. A synchronized block locks only the designated critical section lines.
• Lock Target: Synchronized instance methods always lock on this. Synchronized blocks can lock on any custom object (such as a private final Object lock).
• Performance: Synchronized blocks provide finer granularity, allowing non-critical code to execute in parallel, yielding much higher concurrency throughput.
Q2. What is lock reentrancy and why is it essential? ▼
Answer: Lock reentrancy means that if a thread already owns a lock, it can re-acquire the same lock without blocking or deadlocking itself. In Java, all intrinsic monitor locks are reentrant. If Java locks were not reentrant, a synchronized method calling another synchronized method on the same object would freeze forever waiting for itself to release the lock!
Q3. Can two threads execute two different synchronized instance methods on the same object at the same time? ▼
Answer: No! Both synchronized instance methods lock on the exact same monitor lock: this. While Thread 1 is executing methodA() on object obj, Thread 2 attempting to invoke methodB() on that same obj will be blocked until Thread 1 finishes and releases the lock on obj.
Q4. Can two threads execute a static synchronized method and an instance synchronized method simultaneously? ▼
Answer: Yes! Because they lock on two completely different objects:
• The static synchronized method locks on the class object (MyClass.class).
• The instance synchronized method locks on the instance object (this).
Since the locks are distinct, the two threads will NOT block each other.
Q5. Why should lock objects always be declared 'private final Object'? ▼
Answer:
• private: Ensures no external client code can see or synchronize on your lock, preventing accidental interference and denial-of-service deadlocks.
• final: Guarantees the lock object reference can never be reassigned. If a lock reference changes while threads are running, different threads would synchronize on different objects, destroying mutual exclusion!

📌 Core Summary & Key Takeaways

  • Synchronized Methods: Coarse-grained locking on this (instance) or Class.class (static).
  • Synchronized Blocks: Fine-grained locking on a designated object; allows non-critical logic to execute in parallel.
  • Private Final Lock Pattern: Best practice to prevent external code from interfering with internal synchronization.
  • Avoid String/Integer Locks: String pooling and boxed caching cause unexpected cross-application lock contention.
  • Reentrant Locking: A thread can re-enter synchronized blocks guarded by the same lock without self-deadlock.
